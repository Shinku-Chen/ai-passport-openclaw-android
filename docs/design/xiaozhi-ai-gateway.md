# 小智 AI 网关（Xiaozhi AI）设计方案

> 状态：**待评审**（2026-10-03 起草）。评审通过后再动代码；本文只描述设计与验证计划。

## 1. 目标

在 App 的「网关设置」里增加**第五种网关类型：小智 AI**，把现有小智会话从「只做语音识别（STT）」
延长为**一条完整的 小智 AI 流程**：上行语音 → 小智 ASR → 小智 LLM → 小智 TTS → 回复上屏 + 语音在设备上播出来。

- 后端：**官方小智云**（复用 App 里已有的激活流程与凭据，见 `stt/XiaozhiActivator.kt`）。
- 语音：**小智的 TTS 音频原样转发**给设备播放（音色 = 小智；音频在手机侧整段缓冲，见 §4.4），手机不再本地合成 TTS。
- 形态：**纯 App 改动**，固件不需要改、不用刷机（论证见 §3）。
- 与现有三种网关（OpenClaw / Hermes / 自定义 OpenAI 兼容）**并列**，不改变它们的行为。

### 非目标（本期不做）

- 小智的 MCP / 工具调用扩展、自建小智服务器（地址可留作二期）、音色与角色选择、情绪字段上屏。
- 不改动固件的 BLE 协议、分区、上屏格式与省电行为。

## 3. 协议要点与两处已核对的结论

一条小智会话里同时承载四件事（同一 WS）：

1. **上行**：设备音频 → App → 小智（opus 16 kHz/60 ms，现有实现已跑通）。
2. **识别**：`{"type":"stt","text":…}` —— 现状只用这一条。
3. **回复**：`{"type":"llm","emotion":…,"text":…}` 与 `{"type":"tts","state":"sentence_start","text":…}` —— 本设计新增使用。
4. **语音**：`{"type":"tts","state":"start|sentence_start|sentence_end|stop"}` + **二进制 opus 音频帧** —— 本设计新增使用。

**已核对的结论（决定「不用改固件」是否成立）**：

- 小智 hello 自报 `audio_params: {format: opus, sample_rate: 24000, frame_duration: 60}` → **TTS 音频是 24 kHz**。
- 固件侧：`main/oc_tts.c` 明确接受 `rate_khz == 16 || 24`；`main/oc_audio.c` 在速率变化时
  **重新 `opus_decoder_init(rate)` 并重开 codec**（`bsp_audio_set_format(rate*1000,16,1)`），PCM 帧长按
  `rate_khz` 计算 → **24 kHz 的 TTS 音频可以被原样解码播放**，无需固件改动，也无需手机侧重采样/重编码。
- `TTS_OPUS` 帧格式为 `[SEQ][rate_khz][frame_ms] + opus`（`main/oc_proto.h`），App 侧只要把
  小智的「sample_rate/frame_duration」映射进这两个字段即可。

```text
设备(BLE) ── opus 上行 ─┐
                        ├─ XiaozhiSession（新：从 XiaozhiStt 抽出的 WS 会话层）

                                ├─ STT：{"type":"stt"} → 文本

                       │                                  │
      ┌────────────────┼────────────────┐        （OpenClaw / Hermes / OpenAI 兼容）
      │                │                │
```

### 4.1 会话抽离

（✅ 已完成）WS 连接、hello、opus 编码、预热、重连重放已从 `XiaozhiStt` 抽到 `stt/XiaozhiSession.kt`，
`XiaozhiStt` 退化为「只负责 `stt` 事件 → 文本」的适配器（现有行为与日志保持不变）。
`XiaozhiSession` 暴露三组回调：`onStt(text)` / `onLlm(text)` / `onTtsState(state, text)` / `onTtsAudio(opus, rateKhz, frameMs)`。

### 4.2 新增网关类型与模式

「小智 AI」与其他三种网关的本质区别：**它不是「文本进、文本出」**，而是自带 ASR/TTS 的整条链路。
因此实现上不是简单再加一个 `GatewayAdapter` 实现，而是：

- 设置里仍然叫「网关类型 = 小智 AI」（满足用户心智：它就是一个可选的 AI 后端）；
- `VoicePipeline` 增加 `mode = LocalStt | XiaozhiDirect`：选中小智 AI 时走 `XiaozhiDirect`，
  一轮的输入直接是**设备音频**（不经过 App 的 `SttEngine` 抽象），输出是正文 + TTS 音频。
- `GatewayAdapter.chatMulti(text)` 在小智模式下**不再被调用**；`XiaozhiGateway` 只把
  「正文」与「TTS 音频」两路回给管线（接口收窄为 `onReplyText` / `onTtsAudio`，便于单测）。

### 4.3 TTS 直通

- 复用 `TtsFlowControl`（在途上限、领先量）与 `DeviceTtsSession` 的下行发送、`tts_start`/`tts_stop`/`tts_abort`、
  以及设备回报（`tts_playback_done` / `tts_playback_aborted`）对账。
- **跳过** `TtsFraming` 的本地「PCM → Opus」：小智已给出 opus 包，直接按
  `[SEQ][rate_khz=24][frame_ms=60]` 组 `TTS_OPUS` 帧。
- 小智的 `sentence_start` → 设备 `tts_start`（句级流式，不整段等）；`tts.stop` → 设备 `tts_stop`。

### 4.4 返工（2026-10-04 修正版：正文先上屏 → 紧接着开播 → 边播边缓冲）

> **注意（2026-10 最终口径）**：本节描述的「**一轮一条连续音频流**」已被 **§4.8 按段播放**取代 ——
> 现在一轮有**多段**（段 = 小智的一句），每段一对 `tts_start`/`tts_stop`，段间等设备回报
> （或兜底超时）。本节以下关于「窗口在 `stop` 之后保持打开 / 迟到帧即时下发 / 尾部收尾」的描述，
> 在按段模型里分别对应「**最后一段不收段**（尾帧照收）/ 段内迟到帧归本段 / 推空+静默达 3s 收本段」。
> 保留本节作为当时（一轮一段时期）的设计记录。

作者定的操作流程：**TTS 缓冲；整段文字上屏之后就开始播放 TTS；TTS 不需要保证整段 ——
一边播放一边缓冲也可以。**

> 这里修正了同一天上一版的两处理解偏差：① 不是「等整段音频齐才开始播」；② `stop` 之后到达的
> 音频帧**不能丢弃**，要照常下发。
>
> **增补（2026-10，作者定稿「第一句就好」，后统一为**每段独立上屏**）**：正文改为 **按段上屏**（见 §6）
> —— **首段一上屏就开播**，屏幕文字一段一段地跟着上（**不累计**：A → B → C，不是 A → AB → ABC）；
> 延迟 ~16s → ~3s。因此本文下面写「整段文字上屏之后才开播」的时机，
> 一律按**第一段**理解；§4.4 的其余机制（音频缓冲、上屏信号闸门、`stop` 之后迟到帧照常下发、
> 尾部收尾）全部不变。**已知取舍**：提前到首段开播会重新暴露早期「首句即开段」的听感风险
> （句与句之间的 TTS 生成间隔可能造成设备侧短暂欠载）；作者已按「延迟优先」拍板，后续如需再调另开一轮。
>
> **实现位置**：按段交付＝`XiaozhiReplyText.deliverOpenLocked`（每来一句只交**它自己**的文本，触发者
> `首段` / `第N段` / `第N段更新`）；音频侧不需要改闸门 —— 它本来就在「本段正文已上屏」信号上开播，
> 只是那个信号现在首段就能发出。

一轮的时序（小智模式）：

1. 按下 OK → `turn_start` → 设备 `tts_abort` + **关上一段播放窗口** + **清空本轮音频缓冲/待播队列**；
2. `tts` 句级文本照旧喂给 `XiaozhiReplyText` 装配：**每收到一句就把这一句自己的文本交付一次**
   （清洗后非空可读，**不累计**前后句；同一句在 `sentence_end` 变完整时只更新本段）；
   音频帧全部进入 `XiaozhiTtsRelay` 的缓冲，**一个字节都不下发给设备**；
3. **第 1 段正文上屏**（流水线把该正文写成 `TEXT('A')` 之后）：
   - 文字：第 1 段（已清洗，见 §6.2）上屏，一条气泡；
   - 音频：**紧接着开播** —— 下发 `tts_start` → 按既有节奏（`TtsFlowControl` 的在途上限/领先量，
     **参数语义不变**）把**已缓冲**的帧按到达顺序连续推给设备；
   - 之后每段到达：文字侧**各发一帧 `TEXT('A')`**（**只发这一段自己的文本**；App 气泡就地替换），
     音频侧按 §4.8 的段闸门逐段开播；
4. `{"type":"tts","state":"stop"}` 到达 = **文本侧最终结算点**：各段都已上屏则**不产生新正文**
   （**绝不重发累计全文**）；只有某段从未上屏时才**只补那一段**；**不**关音频窗口；
5. **播放窗口在 `stop` 之后保持打开**：`stop` 之后继续到达的音频帧**照常下发**（这就是「一边播放
   一边缓冲」），SEQ 连续；
6. 本轮收尾才 `tts_stop`，四条路径都要能收（**幂等**）：新一轮 `turn_start` / barge / 设备
   `turn_cancel` / **设备回报播放完成**（`tts_playback_done` / `tts_playback_aborted`）；
   另加一条**不依赖设备回报**的确定收尾（见下方「尾部收尾」）。打断同样丢弃全部未播缓冲
   （**绝不**把上一轮的音频排进下一轮）。

**顺序保证（正文必须先于第一个音频帧到达设备）**：开播不由 `stop` 直接触发，而是等一个明确的
**「本轮正文已上屏」信号** —— `VoiceBridgeService.sendTextFrame('A', 正文)` 把该条正文分片**写进
BLE 串行写队列之后**调 `XiaozhiTtsRelay.onReplyTextDisplayed('A', 正文)`（按段交付下这条正文就是
**第 1 段**的字幕）。正文帧与音频帧走同一个串行
写队列，所以「正文先于首帧」**由构造保证**，不是靠毫秒级时序（JVM 单测里有顺序断言）。`stop` 之前、
以及上屏信号之前到达的帧一律只缓冲。

信号必须与**本轮正文**对得上号（2026-10-05 真机修正；判定是纯函数 `XiaozhiScreenSignal`）：

- 会话层在装配好本段正文时先调 `XiaozhiTtsRelay.onReplyBody(body)`（按段交付下**每段都调**，
  直通侧把本轮所有交付过的正文都记下来）；
- 只有 `role == 'A'` **且**上屏文本与**本轮已交付的某条正文**一致才算信号。`'U'`（识别原文）、`'R'`（系统提示），
  以及同为 `'A'` 的**版本提示 /「无语音」/ 网关超时与失败原因 / 空回复兜底**一律不开播 ——
  否则本轮音频会抢在真正文前面出声（或跟一条与音频无关的提示一起播）；
- 记多条的用途：按段交付下第 1 段那条 `TEXT('A')` 可能还在流水线/写队列里排队时，下一段的正文
  已经到达；只认「最后一条」会把**第 1 段**信号误判成「不是本段正文」而拒绝开播，正好破坏「首段即开播」；
- 本轮正文为空（只有表情/模板）→ 任何 `'A'` 都不开播（没文字就没有「文字先于声音」可言）；
- 每轮 `turn_start` 清掉本轮正文记录 → 上一轮**迟到的**同文本信号也打不开新一轮的闸门。

- 正文比 `stop` 早结算时（空闲兜底窗口先上屏），信号先到、`stop` 后到 —— `stop` 到达即开播。
- `turn_start` 路径上流水线**已经**先发了设备 `tts_abort`，所以直通侧收尾的 `tts_stop` 是空操作；
  `barge` / 设备 `turn_cancel` 没有 `tts_abort`，收尾的 `tts_stop` 就是窗口的正常关闭信号。

缓冲上限与超限策略（`XiaozhiTtsRelay.MAX_BUFFER_FRAMES`）：

- 取值 **300 帧 = 18s 音频**。理由：够覆盖常见回复（两三句、约 80–110 汉字）；内存有界
  （每帧 ≤ 512B opus + 3B 帧头，峰值 ≤ 约 155KB）；且必须**小于**服务侧待发队列上限
  （`VoiceBridgeService.MAX_XIAOZHI_TTS_QUEUE_FRAMES`，由 240 提到 **400**）—— 开播时是一口气把
  这几百帧交给服务侧队列，队列必须留得下它们 + `tts_stop` 标记。
- 上限只约束**正文上屏之前**的缓冲；`stop` 之后等上屏信号的毫秒级窗口与开播之后的帧都不再受它
  约束（交给既有 `TtsFlowControl` 在途上限）。
- **超限丢最旧的一帧**（内存必须有界）并记节流日志：**绝不**为了「不丢音频」而提前开播 ——
  顺序优先于完整（作者要求：降级时宁可稍晚也别抢跑）。
- **只推二进制音频、一条 `tts` 状态报文都没有的服务端**（实测存在）既没有窗口、也没有「整段正文齐」
  的信号；这种帧**不按窗口丢弃**，但**仍然只缓冲**、等「正文已上屏」信号（那个信号由正文装配器的
  空闲兜底窗口 / `llm` 兜底上屏时发出）。若一个信号都没来（本轮压根没有可上屏正文），这段音频按
  「窗口外」丢弃，而不是抢在文字前面出声。
- **已知取舍**：**不**用「空闲」当整段正文齐的凭证（开播时机只由**文本交付 + 上屏信号**决定，
  与「空闲多久」无关）—— 句子之间本来就可能隔几秒。因此发了状态报文却
  **漏发 `stop`** 的服务端下，音频等「正文已上屏」信号（正文按 §6 的强制兜底窗口/`llm` 兜底上屏，
  见 §6.4：那种服务端要等到 20s 的强制兜底）一到就开播；实测云端在 `sentence_end` 后毫秒级就发
  `stop`，属退化路径。

**尾部收尾（2026-10-05 真机修正：设备不能一直停在「接收中」）**：窗口在 `stop` 之后是开着的，
而正常关闭点原本只有「设备回报本段播完」—— 设备不报（旧固件/解码失败/回报丢失）时，手机上早就
推完了，设备还停在播放态。现在服务侧 drain 循环加一条**确定**收尾（纯判定 `XiaozhiTailStop`）：

- 本段**已真推出过帧**、且**已推空**（队列里没有待写帧）后**静默达 `TAIL_IDLE_MS`（3s）** →
  主动叫 `XiaozhiTtsRelay.onIdleTailStop()` → `tts_stop`（设备把已入队的播完就退出播放态）。
  3s = 流控硬上限 2s（最后一帧写出后设备最多还需这么久播完）+ 1s 余量；
- 这条路径**不关直通窗口**（`segmentOpen`/`textScreenPassed` 保留）：后续迟到帧仍会照常下发
  （必要时自动补一个 `tts_start` 续一段），所以**不会把尾音切掉**；
- 幂等：一段只收一次；又有新帧时计数器归零、收尾资格作废；设备回报仍是「真的播完了」的主路径。

- **已知风险（待真机核对）**：以「设备回报播放完成」收尾窗口 —— 若固件在**解码队列暂时排空**时
  就回报（而不是一段结束），尾音可能被提前切掉。按 `docs/wire-protocol.md`，`tts_playback_done`
  是「一段播完」，本设计据此实现（见 §9 真机项）。注意上述「尾部收尾」是 3s 静默兜底，
  真机上应核对它**不会**在设备还在播时发出（看 `主动收尾` 那行日志与设备侧表现）。

### 4.5 写模式与推送节奏（2026-10 真机确诊：无响应写不可用）

**结论：小智直通的音频帧固定走「带响应写」（`WRITE_TYPE_DEFAULT`）。** 契约常量
`tts/TtsWriteMode.XIAOZHI_DIRECT`（= `WITH_RESPONSE`），`VoiceBridgeService.drainXiaozhiTts` 按它调
`ble.setBulkWrite(false)`，并且**不再**切到无响应写（JVM 单测 `TtsWriteModeTest` 钉住）。

**确诊过程（同机 + 同固件，两步 A/B）**：

1. 症状：App 日志逐帧报「写入成功」，设备侧 `TTS` 计数**恒为 0**（同链路的 `TXT`/`CTRL` 都正常），
   而设备日志里的 `RX 缓冲满` 计数**也是 0** —— 这一条排除了「RX ring（4KB）被灌爆」的解释，
   说明帧根本没到设备；
2. 唯一的差别是写类型：音频帧走 `WRITE_NO_RESPONSE`（Write Command，**没有 ATT 应答，丢了也不报错**）。
   把 drain 改成带响应写后，设备侧立刻出现 `帧到达 … TTS=215`，App 与设备的帧数对得上 →
   **根因就是这一跳的写类型**。

**被推翻的旧假设**：代码里长期写着「带响应写是串行的，一次连接事件只能推一个包 → 只有 11 帧/秒，
低于实时所需的 16.7 帧/秒 → 设备会饿死」，并据此在两条下行路径上都切到无响应写（历史上还因此
出现了「设备朗读开关被自动关掉」）。实测（同一次 A/B）带响应写 **207 帧 / 11.2s ≈ 18.5 帧/秒**
——**高于**实时需求。附带收益：只有带响应写才有 GATT 写回调，
`BleCentral.deliveredFrameCount()` 才是真实在途量，流控的在途上限才有意义。

**推送节奏（消除设备侧 `欠载`）**：同一轮 A/B 里设备回报 `收=215 解=214 丢=1 欠载=32`。服务端已经
把整段音频生成好、App 手里有全部帧，欠载只可能来自推送节奏 —— 只按「领先量」（已推音频 − 已过实时）
节流时，App 的推送速率仅比实时快约 10%，于是设备侧的垫底音频在**十几秒内**都贴近空转，任何一次写
回调/调度抖动都直接变成一次欠载。现在按 `TtsFlowControl.pushWaitMs` 两条一起上（参数取值理由写在
该对象的 KDoc 里）：

- **开播瞬时预充 `PRECHARGE_FRAMES` = 12 帧（≈720ms，2026-10 从 6 帧加厚）**：前 12 帧不受帧间下限约束，
  一口气推给设备。**加厚的原因**：开局要吸收两件事 —— ① 设备把**多行正文**渲染上屏那几十毫秒里
  BLE RX 排不空（就是本次的 `欠载=23`）、② 带响应写 ≈54ms/帧的起步抖动；6 帧 ≈360ms 扣掉最坏在途
  （8 帧 = 480ms）后设备侧仍然会见底。**上限的约束**：设备解码队列是 24 包 ≈1.44s，12 帧占**一半**，
  另一半留给「设备自身约 450ms 的起播 priming 期间仍在到达的帧」（真机开局日志里出现过
  `解码队列满,已丢最旧的包` —— 溢出丢的是用户**还没听到的**音频），所以取区间下限 12 而不是 16。
  **不推迟「文字上屏 → 立刻出声」**：首帧照发，预充只影响第 2–12 帧的发射时刻（那时领先量 ≈0，
  连领先量那条也不等待）；预充最多把领先量抬到 720ms，离目标 1200ms / 硬上限 2000ms 都还有余量。
  **被否决的替代**（见 `TtsFlowControl.PRECHARGE_FRAMES` 的 KDoc）：
  「先发正文帧 → 固定等 X ms → 再推音频」会把首帧音频推到 X 之后，直接破坏「首句上屏后立刻开播」；
  「按正文长度决定预充」的长度只是渲染耗时的弱代理（多行/字形才是主因），收益不确定却要多一条分支。
- **与领先量无关的帧间下限 `MIN_SEND_INTERVAL_MS` = 50ms（20 帧/秒）**：`wait = max(领先量等待,
  sent × 50ms − 已过时间)`。它给推送速率封顶（领先量只封**上限**，不封**速率**）：
  50ms 比实时（60ms/帧）快 20%，垫底音频以 +200ms/s 增长（欠载就发生在「垫底还没攒起来」的窗口，
  所以取用户给定 50–55ms 区间的下限）；50ms 又略快于实测吞吐（≈54ms/帧），因此在本机/本固件上它
  **不生效**（真正限速的是 BLE 往返），不会成为段落中段的新瓶颈；而 MTU 吃满后（一帧一次 ATT 写
  就能发完）它能把速率压在 20 帧/秒以内，不把对端 4KB RX ring 与 24 包解码队列一次灌满
  （领先量上限仍硬封着「最多领先 2s」）。
- **在途积压等待改为有界（`MAX_INFLIGHT_WAIT_MS` = 1s）+ 日志**：原来「最多等 1s 就继续灌」是静默的，
  现在到点照旧放行，但会打一行 `在途积压等待到上限 1000ms(…)`。等待本身也抽成纯判定
  `TtsFlowControl.backlogWaitMs`（在途超上限时按 5ms 轮询，到点必定放行）—— 无限等会在链路半死时
  把整段卡死（写回调自身有 2s 超时兜底）。

**写分片按协商到的 MTU 取（`ble/WriteChunking`）**：`min(mtu − 3, 253)`，还没协商到/协商失败回退 240；
`onMtuChanged` 记下实际值，并打一行 `MTU=… status=… → 单次 ATT 写片长=…`。253 = 256 − 3：把分片压在
本链路验证过的 256B 档位以内，更大的 MTU 不会让单次写变大。

> **真机待核对（本项的直接收益取决于协商结果）**：请求的 MTU 仍是 247（`BleNus.REQUEST_MTU`），
> 片长因此是 244 —— 一个 249B 的 `TTS_OPUS` 帧**仍然要 2 次 ATT 写**（244 + 5）。要拿到「1 次写完」
> 需要协商到 MTU ≥ 252（片长 ≥ 249），即把请求的 MTU 提到 ≥252；这属于另一项改动，先看新的 MTU 日志
> 行确认设备/协议栈实际能协商到多少，再决定要不要提。

### 4.6 正文上屏让路（2026-10 真机现象：屏幕文字变动时语音卡顿）

> **与 §4.8（按段播放）的分工（2026-10 最终口径）**：段与段之间的停顿、字幕与它自己那一段音频的
> 先后，都由 §4.8 的**段闸门**（relay）保证；本节只剩一个作用：**别在一段音频正紧的时候去动文字**
> —— 真机实测的「文字一变就卡一下」就是这么消掉的。§4.7 的**句级对齐门已被删除**（见 §4.7）。

**现象与已定性的两条机制**（作者报告，本轮不再重复取证）：

1. **手机侧**：正文帧与音频帧**共用一条 BLE 串行写队列**（带响应写下一个音频帧 ≈54ms）——
   正文帧插队会让音频多等，而且正文帧到达设备那一刻会触发一次渲染；
2. **设备侧（只读事实，本轮不改固件）**：BLE RX drain 与 LVGL 文本渲染在**同一个应用任务**
   （固件 `oc_app.c`）—— 渲染多行正文那几十毫秒里 RX 排不空 → 解码队列见底 → `欠载`。

真机数字（`xz_test13.log`）：一次播放 `收=249 解=246 丢=3(溢出=3) 欠载=23`；上屏文本多为
125–201 字节多行，且紧贴播放开始 —— 开场那一卡最明显。

**策略：文字让路给声音。** 设备渲染是固件侧的事，手机侧唯一能做的是「**别在音频紧的时候去动文字**」：

- **第 1 段（首段）上屏不受任何影响** —— 它是本段开播的前置条件，必须照旧立刻上屏并开播；
- **后续各段的字幕只在音频不紧时下发**（`tts/XiaozhiCorrectionPacer`，纯逻辑 + JVM 单测）：垫底
  < `LEAD_HOLD_MS` = 900ms、或在途 ≥ `INFLIGHT_HOLD_FRAMES` = 4 帧、或距上次上屏不足
  `MIN_CORRECTION_GAP_MS` = 600ms 时**暂缓**；攒着的多次请求**合并成最新的一条**；兜底
  `MAX_HOLD_MS` = 10s 防止「音频那一路病态」时文案无限期消失。参数取值理由逐条写在
  `XiaozhiCorrectionPacer` 的 KDoc 里。
  **上一版的「一轮最多 3 次主动补正」与「句级对齐门」都已删除**（见 §4.8）：按段播放里
  **每一段的字幕都是它那一节音频的前置条件**，攒到收尾就等于让那几段音频也停在那里；
  而时刻对齐由段的边界（设备回报）决定，再按播放进度卡时刻只会把字幕押迟到。
- **本段音频推完时无条件吐出**：本段 `tts_stop` 写出时（`finishXiaozhiSegment`）把攒着的正文
  **无条件**补上屏 —— 让路只能让文字变晚，不能让文字最终不完整（而按段播放里它还要决定
  下一段能不能开播，所以更不允许长期攒着）。
- **实现位置**：`VoiceBridgeService.sendTextFrame` 在**写入之前**拦一次
  （`deferCorrectionWhileAudioIsTight`），拦不拦的判定只认「小智本段正文的上屏」
  （`XiaozhiTtsRelay.replyScreenOrdinal` ≥ 2，与日志里的「第 N 段字幕上屏」同一套规则）；
  放行与补上走**同一条**写入路径 `writeTextFrame`（不会出现「让路那条路忘了发上屏信号」）；
  音频侧的快照由 `DeviceTtsPush.audioPacing()` 给出（垫底/在途/距上一音频帧写入/队列长度，
  判定与日志共用同一份数据）。其它四种网关一行不改（没有直通音频在推，让路没有意义）。

**被否决的候选**：

- **把补正延迟到 `tts.stop`（退回整段一次性上屏）**：直接废掉「第一句就好」，回到用户感觉
  「音频响应慢」（~16s）的老问题；
- **暂停/降速音频推送来给文字让路**：设备侧会真的欠载（音频断流），比一次渲染停顿更糟；
- **在设备侧把渲染挪出 RX 任务**：那是固件改动（本轮明确不做）；
- **用「正文长度」预估渲染停顿、只在超过某长度时让路**：长度只是弱代理，而且**每一条**补正都会
  插队一次队列 —— 按「音频当下紧不紧」来判更直接，也不用猜设备的字体渲染耗时。

**同类风险（本次不改，待真机复核）**：**本机合成**那条下行路径（`pushAudio`）仍用无响应写
（`TtsWriteMode.LOCAL_SYNTHESIS`）—— 同一台手机 + 同一固件上它很可能同样静默丢帧。它有自己的
合成/编码节奏与验收，本次**不改它的写模式**（调用点只是从字面量 `true` 换成同名契约常量，取值不变），
只加注释标记，列入真机待复核项。

### 4.7 句级字幕对齐（2026-10，**已被 §4.8 按段播放取代**）

> **本节已作废（保留作对照）**：它解决的是「**一轮一条连续音频流**」下字幕要贴到「它自己那句的音频
> 起点」的问题 —— 而那个问题时至今日已经不存在了：§4.8 的按段播放里，**每一段自己就是一句**，
> 段的边界由**设备回报**决定，字幕又是**段的开播前置条件**（第 N 段的 `tts_start` 只在它的字幕已写进
> BLE 写队列之后才发）。所以：`SENTENCE_PRELOAD_MS`、`playedAudioMs` 与
> `XiaozhiCorrectionPacer` 里的**句级对齐门**都已删除；`XiaozhiTtsRelay.sentenceStartMs` 保留下来
> 只作为**取证（日志里 `该句起点≈Yms`）** —— 真机靠它与「第 N 句的音频起点 ≈ 第 1..N−1 句的音频总量」
> 对照。下面几段是当时的口径，已被取代。

作者的时序要求（小智是一句一句来的）：**先上第 N 句字幕 → 紧接着就是第 N 句的声音 → 它播完 →
再上第 N+1 句字幕 → 再上第 N+1 句的声音。**

- **第 1 句不变**：正文可读就**立即上屏 + 立即开播**（§4.4 的唯一闸门，本节的判定不碰它）；
- **第 N（≥2）句**：字幕在「**它自己那句音频即将开播**」时上屏，而不是一收到文本就上屏 ——
  即字幕落位**贴着该句音频起点**；
- **声音仍是连续流**：句与句之间**不留空档、不切段、不重发 `tts_start`**；改的**只是字幕落位时刻**。

**句边界怎么切（音频帧没有句界标记）**：音频帧是 `[SEQ][rate_khz][frame_ms] + opus` 的纯流，
没有任何句界标记。App 唯一能测的句界是「**这一句的正文交付那一刻，本段已经收到了多少帧**」——
由此第 N 句的音频起点 ≈ 「第 1..N−1 句的音频总长」。实现：`XiaozhiTtsRelay` 在 `onReplyBody(body)`
（会话层渐进交付每一条正文时都会调，见 §6.0）记下「已推帧数 + 待推缓冲帧数」，即该条正文的音频
起点（`XiaozhiTtsRelay.sentenceStartMs(body)`；每轮 `turn_start` 清空）。噪声句（只拿到模板/emoji、
不产生交付）**不记**边界 —— 它本来就没有字幕。

**上屏时机判定（App 自己可测的量）**：用**设备播放进度估计**与**该句音频起点**比 ——
`playedAudioMs ≥ sentenceStartMs − SENTENCE_PRELOAD_MS`（=800ms）时才上屏。其中
`playedAudioMs = 已推送音频时长（帧数 × 60ms） − 垫底`（= 自 `tts_start` 起的实时时长，
见 `XiaozhiAudioPacing.pushedAudioMs` / `playedAudioMs`）。

- **为什么用播放进度而不是「已推送音频时长」**：流控让推送时钟**领先**设备播放一个垫底量
  （目标 1200ms、硬上限 2000ms）。拿推送时钟与「起点 − 800ms」比，字幕会比它那句的声音早出
  好几百毫秒（甚至早过一整句），正好破坏「一句一句来」；播放进度 = 推送时钟 − 垫底，才是
  「设备现在听到哪里」的最近似量（垫底/在途/推送时长全部由 `DeviceTtsPush.audioPacing()` 给出，
  判定与日志共用同一份数据）。
- **800ms 提前量的理由**：这条 `TEXT('A')` 与音频帧**共用一条 BLE 串行写队列**，插入时要排在
  **在途（≤`TtsFlowControl.MAX_INFLIGHT_FRAMES`=8 帧 ≈480ms）** 之后，再加设备侧一次多行正文的
  渲染（几十毫秒）—— 两项合计 ≈0.5–0.6s；字幕宁可早一点（声音还没到）也**绝不可晚**（声音已到
  字幕还没上），取作者给的 0.5–0.8s 区间的**上界 800ms**。它又远小于一整句音频，不会把上一句的
  听感盖掉。判定与日志同源（`XiaozhiCorrectionPacer.waitingForSentenceStart` /
  `XiaozhiPacingLog.line`）。

**没有可对齐的音频时一秒都不拦**：非小智网关 / 设备朗读开关关闭 / 服务端只给文本不给音频时，
`XiaozhiTtsRelay.sentenceStartMs` 返回 **null**（本轮一帧**可下发的**音频都没收到），补正照旧
**立刻**上屏 —— 不能为了等一个永远不会到来的音频到点而把文案拖到收尾/兜底时限。

**误差来源（音频可能略滞后于文本）**：服务端先发该句文本、再合成并流式推音频，所以「交付那一刻
已收到的帧数」**低估**该句起点 → 字幕偏**早**（安全方向：字幕一定先于它那句的声音）；低估量通常
只有一小段音频（音频略滞后于文本的那一点），而 800ms 提前量另有 0.5–0.6s 的队列/渲染余量。

**兜底完整性（不许退化）**：某句音频还没到 / 切不出边界 / 判定没触发 / 轮次被打断时，沿用既有兜底 ——
收尾（`XiaozhiCorrectionPacer.flush`）**无条件**把最终完整正文补上屏；任何上屏的文本仍走 §6.2 清洗；
同一轮多次上屏仍走「补正」语义（就地替换/补全）。

**日志（每次字幕上屏一行）**：

```
第 N 句字幕上屏(第 N 次上屏/补正) | 已推送音频≈Xms | 该句起点≈Yms | 音频垫底≈Z 帧(≈Wms) | 在途=I | 距上一音频帧写入 Tms | 队列=Q
```

### 4.8 返工（2026-10 作者最终口径：**按段播放**）

作者的最终口径：**原版小智能区分段落，按段落播放对应语音** —— 不是「整轮一串音频一直连续着」。
所以 TTS 从「**一轮一个段**」改成「**一轮多个段**」，与它同步的**文字侧也从「渐进补全」改成
「每段独立上屏」**：

```
句1 文本到 → 字幕上屏(只上屏句1自己的文本) → tts_start → 推句1的音频帧 → 推完发 tts_stop
        ↓ 设备回报「这一段播完」(tts_playback_done;或超时兜底)
句2 文本到 → 字幕上屏(只上屏句2自己的文本) → tts_start → 推句2的音频帧 → tts_stop → …
        ↓ 最后一段播完 → 本轮收尾
```

- **每段字幕 = 那一段自己的文本**（A → B → C）—— **不累计**（旧实现的 A → AB → ABC 会让屏幕
  上多出 AB、ABC 这些**重复气泡**）。会话层（`stt/XiaozhiReplyText`）每收到一句就只交**这一句自己的
  文本**；`sentence_end` 带来的更完整文本只**更新本段**（段号不变）。
- **段边界仍用小智自己的分句**（`tts[sentence_start]` / `[sentence_end]`）——
  它是 App 唯一能测的句界（音频帧是纯流，**没有**句界标记）。落点：
  `sentence_start` = 新的一句开始（它带着这一句刚交付的正文，于是上一段收口 + 开新段）；
  `sentence_end` 带来的更完整正文 = **同一段**的字幕更新（`start` 给半句 / `end` 给整句那种），
  **不切段**。服务端从不发状态报文（纯音频服务端）时退化为「每次正文交付就是一句」。
  旧记账（「交付某句正文那一刻已收到的帧数 = 该句音频起点」）仍保留为**证据**
  （`XiaozhiTtsRelay.sentenceStartMs`，进日志的 `本段起点≈Yms`）。
- **段间是自然停顿**：一段 `tts_stop` 之后**等设备回报**（`tts_playback_done` / `tts_playback_aborted`）
  才开下一段；设备不回报时按**本段自己的音频长度**估 ——
  `XiaozhiSegmentWait.reportWaitExpired(自本段 tts_start 起的毫秒数, 本段已推帧数)` =
  `≥ max(帧数×60ms + DEVICE_MARGIN_MS(1500ms), MIN_WAIT_MS(2000ms))`。
  余量 1500ms 吸收设备起播 priming（≈450ms）、最后一帧的写/播放尾与回报的 BLE 往返；
  宁可等到估计播完再推进 —— 推进意味着对设备 `tts_start` 下一段，抢跑就把两段在设备侧连成一条。
- **字幕与它那一句严格同段**：第 N 段的 `tts_start` 只在它的字幕**已写进 BLE 串行写队列**
  （`onReplyTextDisplayed`，由服务侧在 `TEXT('A')` 分片入队之后调用）才可能发出 —— 顺序由构造保证。
  首段（首句）因此文本 + 音频齐了就**立即开播**（延迟优先，不变）；§4.7 的句级对齐门因此删除
  （段的边界已是权威时刻，再按播放进度卡只会把字幕押迟到）。
- **不许丢音频、也不串段**：一段 `tts_stop` 之后绝不再有帧插进那一段 —— 它们要么在收口前就到齐
  （段内迟到帧照收），要么进「未归属池」成为**下一段**的开头（不丢），要么（**本轮还一段都没声明过**
  且服务端会发状态报文时）判为上一轮/换轮前在途的残帧**丢弃**（换轮绝不串段）。
  整段一帧都没有 → **跳过**该段（不发空的一对括号）。缓冲仍有上限（300 帧，丢最旧）。
- **`tts.state=stop` 不收段、也不重发累计全文**：文本侧 `stop` 是**最终结算点** —— 各段都已上屏就
  **什么新正文都不产生**，只在「某一段从未上屏」时**只补那一段**（日志 `第 N 段字幕(补上:…)`；
  一句都没上屏过时用**累计 tts 文本 / `llm.text`** 整轮兜底，见 §6）。音频侧：实测服务端在 `stop` 之后
  还会推本段的迟到帧，收段会把尾音关在门外；
  最后一段由「**推空 + 设备侧静默达 `XiaozhiTailStop.TAIL_IDLE_MS`（3s）**」收口
  （与既有「尾音不被切」同一套理由：静默 3s ≈ 领先硬上限 2s + 1s 余量，而 `tts_stop` 的语义是
  「把已入队的播完再退出播放态」）。收口之后**再来的帧会续一段**（新的 `tts_start/tts_stop`），尾音不丢。

**实现位置**：`tts/XiaozhiTtsRelay`（段机 + 闸门 + 日志）、`VoiceBridgeService.DeviceTtsPush`
（一段一对括号的 BLE 下发：每段 `tts_start` 时把本段的推送计数/实时基准/在途基准归零 →
每段都有自己的开播预充与领先量预算；drain 循环跨段存活，同时兼任「等设备回报超时」的推送）。
**不改**：固件/协议、写模式（仍固定带响应写）、`TtsFlowControl` 参数、其它四种网关、
识别/绑定/身份/client-id/朗读开关语义。

**日志（真机一眼定位）**：

```
第 N 段字幕上屏(本段 L 字): …   ← 每条正文（= 它那一段的字幕）落位时一行；与「第 N 段已声明」同号
第 N 段字幕更新(本段 L 字) / 第 N 段字幕(补上:…) / 第 N 段字幕(跳过:…,不占段号)
第 N 段开始(帧数=X 时长≈Yms,字幕 L 字) → tts_start
第 N 段收口(下一句文本已到|推空且设备侧静默) / 第 N 段推完(N 帧 ≈Mms) → tts_stop
第 N 段播完回报(tts_playback_done,已转发 N 帧) = <下一段=…|本轮音频收尾>
第 N 段播完回报超时(已推送 N 帧 ≈Mms,等满 Tms):不再等设备 → …
首帧音频写出(距上屏 Xms) 预充=12 帧: …            ← 保留（作者用这个 X 量「首段上屏 → 首帧」）
第 N 段字幕上屏(本段 L 字) | 已推送音频≈… | 本段起点≈… | 音频垫底≈… | 在途=… | …
```

## 5. 一轮的时序（小智模式）

> 时序已按 **§4.8 的按段播放**（2026-10 作者最终口径）+ §4.4 的修正版 + §6 的**每段独立上屏**
> （A → B → C，不累计）+ §4.6 的正文上屏让路更新：
> **每一句各一对括号**（字幕先上屏 → 本段 `tts_start` → 推本段音频 → 推完 `tts_stop`），
> **段间等设备回报或兜底超时**（段间因此是自然停顿），本轮收尾才结束；每轮 `turn_start` 先
> **关段 + 清空全部待播段/帧**。

1. 按下 OK → `turn_start`（设备变红）→ App 立即 `XiaozhiSession.startTurn()`（沿用预热，就绪毫秒级）→
   下发 `turn_ready`（设备变绿）。
2. 设备音频逐帧上行；小智回 `{"type":"stt","text":…}` → **上屏 `TEXT('U')`**（与现有观感一致）。
3. 小智回 `{"type":"llm","text":…}` / `tts` 句级文本 → **按段上屏**：每收到一句就把**这一句
   自己的文本**（清洗后）交付一次（**不累计**）；**首段交付**即上屏 `TEXT('A')`，后续每一段各发一帧
   `TEXT('A')`（App 气泡就地替换，见 §6）。屏幕上因此只有 A → B → C，不会多出 AB/ABC。
4. **每一条已上屏的正文开一段**（段 = 小智的一句，见 §4.8）：
   - 第 1 段：正文上屏（`TEXT('A')` 分片已入 BLE 串行写队列）后**立即** `tts_start`，
     已收的帧按 `TtsFlowControl` 的既有节奏连续推出（作者要的「音频响应快」就是这一段）；
   - 第 N（≥2）段：它的字幕**先落位**（音频紧时按 §4.6 暂缓、合并成最新一条），
     然后 **等设备回报上一段播完**（或兜底超时）才 `tts_start` —— **段间不留重叠**；
   - 段内的迟到帧照收（不丢）；本段收尾 = 下一句文本到达（或最后一段的「推空 + 静默 3s」）→ `tts_stop`。
   注：上屏→开播的先后由「**本段正文**已上屏」信号保证（角色 `'A'` + 文本与本轮已交付的某一段正文
   逐字一致，见 §4.4），其它 `'A'` 文本（版本提示/「无语音」/超时与失败原因）不分段也不开播。
5. `tts.state=stop` → **文本侧最终结算点**：各段都已上屏则**不再产生新正文**（**绝不重发累计全文**）；
   只有「某一段从未上屏」时才**只补那一段**（日志 `第 N 段字幕(补上:…)`）；若它被让路拦下，则与前面
   攒着的一起合并。音频侧**不收段** —— 本段的迟到帧还没到。
6. 最后一段：本段推空且设备侧静默 3s（或设备回报播完）→ `tts_stop`（设备回空闲）；
   本轮收尾（新一轮 / barge / 设备 `turn_cancel`）→ 关掉已开的一段并**清空全部待播段/帧**
   （上一轮的残帧绝不进下一轮）。
7. 用户在朗读过程中再按 OK → App 发小智 `abort` + 设备 `tts_abort`（打断），回到第 1 步。

## 6. 上屏策略（本设计里唯一有取舍的点）

小智的正文按句到达（`sentence_start`），而设备侧一条 `TEXT` 帧就是**一个气泡**，协议没有「就地更新气泡」。

### 6.0 定案（2026-10，作者拍板「第一句就好」，后统一为**每段独立上屏**）：**按段上屏（首段即开播）+ 只补缺**

> **本节标题与内容的修订**：上一版写的是「渐进上屏（首句即开播）+ 补正补全」——「补全」指的是
> **把累计文本越补越长**（A → AB → ABC）。作者随后明确：**屏幕上要一段一段来**（A、B、C 各一条），
> 不要 AB、ABC 那些**重复气泡**。所以现在：每次交付 = **这一段自己的文本**（不累计、不重复），
> `sentence_end` 的同一句更新只更新**本段**，`stop` 只**补缺**。

> **与 §4.8 的关系**：本节管**文字**（每段一条、不累计，App 气泡就地替换）；
> §4.8 管**段**（每一条正文 = 它那一段的字幕，段间等设备回报）。两者同步：第 N 段正文上屏 →
> 第 N 段才可能 `tts_start`（字幕是段的开播前置条件）。

真机时间线证明小智是**逐句生成**的（从第一句到最后一句要 ~16 秒，长回答更久），而把开播放在
`tts.stop`（整段齐）会让用户感觉「音频响应慢」。作者拍板：**第一句文本一上屏就开播**
（延迟 ~16s → ~3s），屏幕文字一段一段地跟着上。

- **首段起按段交付**：每来一句，`stt/XiaozhiReplyText.deliverOpenLocked` 就把**这一句自己的 tts 文本**
  清洗后交一次（段号 = 本轮第几次上屏）—— 第一次交付（触发者 `首段`）就是音频侧开播的信号（§4.4），
  之后的每一段各交一次（触发者 `第N段`；`sentence_end` 把同一句补完整时是 `第N段更新`）。
- **`stop` 是最终结算点，且只补缺**：**各段都已上屏 → 什么新正文都不产生**（`changed=false`，不重复
  上屏）；**某段从未上屏**（它的文本在结算点才到齐/才变得可读）→ **只补这一段自己的文本**
  （日志 `第 N 段字幕(补上:…)`）；本轮**一段都没有**（纯 `llm` 服务端/句级文本全为空）→ 整轮当作一段
  走兜底（**累计 tts 文本优先、`llm.text` 次之**）。tts 清洗后不可上屏时 **stop 上挂起不结算**
  （工具调用静默期，见 §6.4）。
- **硬约束（不许破坏）**：只拿到模板/emoji/空文本时**一个字节都不提前交付** —— 那是「设备屏停在更短
  文本上」的根因；任何一次交付的正文都必须清洗后**非空可读**；逐段交付只认 **tts 句级文本**，
  **不**回退 `llm.text`（只有「本轮一段都没有」的整轮兜底才用它）。
- **设备侧表现**：同一轮会有**多条** `TEXT('A')`（每段一条），协议没有「更新气泡」，所以设备屏上就是
  **A、B、C 三条各自独立的气泡**；同一句变完整时多出的那条是**本段的更新**（段号不变）。
  App 侧则**就地替换**同一个正文气泡，日志用 `首次上屏` / `第 N 段字幕上屏` 区分
  （`VoiceBridgeService.screenPhase`）。
- **各段 `TEXT('A')` 的落位（2026-10 §4.8 按段播放定稿）**：每一条正文就是**它那一段**的字幕，
  而段的开播（`tts_start`）要等它进 BLE 写队列（§4.8 的段闸门）——所以字幕与它那一段的声音
  **严格同段**，且第 N（≥2）段的音频还要再等**上一段被设备报完播完**（段间自然停顿）。
  会话层该交多少段还是交多少段、App 气泡仍是**立刻**就地替换；被§4.6 拦下的只有**发给设备的**
  那一帧（也正是唯一会触发设备渲染的那一跳），而且拦住的只是本段开播前的一小段等待。

#### 历史讨论（已被 6.0 取代，保留作对照）

- 方案 A：用整段文本一次上屏。观感与现有网关一致（一条回复一个气泡），实现最简单；
  代价是比句级晚一点点 —— **当初的「晚一点点」在真机上变成了 ~16s**（逐句生成），所以改为 6.0。
- 方案 B：每个句子一个 `TEXT` → 一串碎气泡，阅读体验差。
- 方案 C：等 `tts.stop` 再整段上屏 → 太晚，设备屏在朗读期间是空的。

6.0 的形态与方案 A 相同（一轮只有**一个**正文），只是**分几次把它交出去**（首句先上，后续补正补齐）。

> **历史注（2026-10 已被上面的「每段独立上屏」取代）**：上一版 6.0 的「分几次交同一个正文、屏幕先短后长」
> 在设备上表现为 A → AB → ABC 的**重复气泡**，作者已明确否掉；现在每次只交**那一段自己的文本**。

### 6.2 上屏正文的清洗（2026-10-04）

整段上屏后，服务端夹在正文里的**工具模板残留**会更显眼（一条气泡里混着 `% get_weather…`）。
因此上屏前过一遍纯函数清洗器 `stt/XiaozhiReplySanitizer`（可 JVM 单测）：

1. `<tool_call>…</tool_call>` / `<tool_result>` / `<function_call>` / `<invoke>` 等**同名成对**的工具块整块删除；
   孤立标签只删标签、**保留**块内文本（宁可可读也不误删正文）；
2. `% 工具名` 整行模板（含 `(…)` / `{…}` 参数，**参数里允许一层嵌套**，如 `location="浦东(上海)"`）删除；
   行内 `% 工具名(…)` / `% 工具名{…}`（必须带参数列表）连同两侧空白删除；行首的**裸模板 token**
   （`% get_weather 明天小雨…`）只删 token、保留同行正文 —— `50%`、`100% 的用户` 这类正文百分号不受影响；
3. `{{…}}`、`${…}` 占位（含跨行）删除（连同两侧空白）；
4. 多余空白归一：连续空格压一个、中文标点旁的空格删掉、连续换行压一个、trim。

清洗**只删模板/占位与空白**，不动任何标点与文字；清洗后为空串时按「本轮没有可上屏正文」
交出空串（走 §6.1 的可读原因路径，不产生空气泡）。正文长度仍沿用既有的 2048B 分片规则
（`VbFrame.TEXT_PAYLOAD_MAX`），**不**在正文层再造一套截断。

**「可上屏」不等于「清洗后非空」**（2026-10-05 真机修正）：`isDisplayable(body)` = 至少含一个字母/数字。
emoji 不会被清洗删掉，而把 emoji 当正文上屏正是「设备屏上一个方块」那个 bug；所以纯表情/纯标点的
回复归入「没有可上屏正文」那条可读原因路径（与设计 §6.1 的「绝不 上屏 emoji」一致）。

### 6.1 修订（2026-10-04，真机取证：正文取哪一路）

真机现象：小智 AI 全链路已通（识别 ✓、TTS 直通 ✓），但**上屏的「回复」只有一个 emoji**（设备屏是方块），
而用户实际听到的正文在 `tts` 的句级文本里（`收到小智 tts[sentence_end]: 气温大概十八到二十三度…`）。
结论：`llm` 报文带 `emotion` 一类非正文字段，**首条 `llm.text` 可能只是表情/首片**，不能当正文。
因此正文来源改为（取代本节的「以 `llm` 为准」与方案 A 的取用方向，上屏形态仍是方案 A）：

1. **首选：`tts` 的句级文本**（`start`/`sentence_start`/`sentence_end` 的 `text`）—— 用户听到什么就
   上屏什么；**按段**交付：每次只交**当前这一句自己的文本**（`sentence_start`/`sentence_end` 各带一次
   同一句时**只算一次**，后者更完整时只更新本段）。
2. **时机（2026-10 定稿：按段上屏）**：每收到一句就把**这一句自己的文本**交付一次（首段即上屏并可开播，
   后续每段各一条，见 §6.0），**不累计**前后段；`tts.state=stop` 是**最终结算点**（各段都已上屏则不重复
   交付，只补没上屏的那一段）。收到过 `tts` 报文之后，空闲窗口
   只作「一直没等到 `stop`」的**强制兜底**（§6.4），不在句与句之间结算；整轮一条 `tts` 报文都没有
   （纯 `llm` 服务端）时才用空闲窗口兜底（那种服务端永远不会给 `stop`）；
3. **兜底：`tts` 那一路没有可上屏文字时用 `llm.text`** —— 包括「一条 tts 文本都没有」与
   「有 tts 文本但清洗后只剩表情/工具模板」两种（真机工具调用轮次就是后者）；
   注意：tts 已给过文本而只是不可上屏时，**`stop` 上仍然挂起**、要到**强制兜底窗口**才回退 `llm.text`
   （中间态文本抢上屏正是 §6.4 要防的）；
4. **`emotion`（或任何非正文字段）永不参与**；两路都没有可上屏文字 → 按失败语义给**可读原因**，
   **绝不**上屏 emoji/空串（`XiaozhiGateway.NO_BODY`）。

### 6.3 修订（2026-10-05 真机问题：同轮已有 tts 句级文本却提示「没有可上屏的正文」）

真机现象：设备屏出现了「小智这一轮没有返回可上屏的正文（只有表情/空文本）」那句兜底文案，
而**同一轮**服务端明明给了 tts 句级文本（如「明天上海是小雨喔，白天23度」），只是 `llm.text` 里混着
`% get_weather…` 与 emoji。两个成因分别修掉：

1. **结算时机抢跑**：工具调用轮次会先推一条只含模板/表情的 tts 文本，真答案要等工具结果回来后才到。
   旧实现「最后一句后 2s 无新增即结算」会把「没有可上屏正文」抢在真答案之前交出去，而真答案到达时
   本轮已结算、被丢弃。现在：**只要收到过 `tts` 报文就只认 `stop`**（空闲窗口退化为长强制兜底，
   §6.4），没有 tts 报文时才用 8s 的 `llm` 兜底窗口；任何新文本一到就重新计时。
   （本条的窗口取值后来被 §6.4 取代 —— `NOISE_ONLY_IDLE_GRACE_MS` 与「有可上屏正文才用 2s」都已不再存在。）
2. **兜底文案写清哪一层为空**：`XiaozhiReplyText` 交出的结果带一句结算说明（`XiaozhiReplyOutcome.detail`：
   tts 句级几条/清洗后多少字、llm.text 多少字/清洗后多少字），`XiaozhiGateway` 把它拼进 `NO_BODY` 原因
   （设备屏与状态卡都会看到），所以这句话**只在确实没有可上屏文字时**出现，且能看出卡在哪一层。

回归单测（`XiaozhiReplySanitizerTest` / `XiaozhiReplyTextTest`）就用真机那几轮的**实际字符串**钉死：
含 `% get_weather…`、emoji、`<tool_call>`、句级拼接时，正文一个字都不能少、也不得退化成空串。

实现与单测：纯逻辑 `stt/XiaozhiReplyText`（装配 + 结算时机）由 `XiaozhiSession` 喂 `llm`/`tts` 两条下行，
结果经既有 `onLlm`/`llmObserver` 出口（小智模式的 `TEXT('A')` 上屏路径不变）；
TTS 直通与设备朗读路径**不动**。

### 6.4 修订（2026-10-06 真机问题：从小智获取的文本不是完整的）

真机现象：小智实际发来的句级文本是完整长句（`tts[sentence_start]`：`明天上海是小雨喔，白天都湿湿的，
晚上才转阴，算不上好天气啦。`），而设备上屏的是更短的一截（含 `% get_weather…` 模板残留的中间态
`llm.text`）。成因有两条，都已修掉（`XiaozhiReplyText` + `XiaozhiGateway` + `VoicePipeline`）：

1. **`stop` 上的「兜底抢跑」**：工具调用轮次的第一段往往只有模板句级文本 + `stop`（真答案在**下一段**）。
   旧实现在这个 `stop` 上就结算了 —— tts 侧不可上屏，于是回退 `llm.text`，那条更短的中间态文本上了屏；
   随后到达的完整句级文本因为「本轮已结算」被整段丢掉。现在：**`stop` 上若 tts 已给过文本、而清洗后
   不可上屏（只有模板/表情），就挂起不结算**（记一行「工具调用静默期挂起」），等后续分段/下一个 `stop`。
2. **结算闩太硬（同一轮只结算一次）**：同一轮里**后面的段**也要能上屏（多段 `tts[start…stop]` 的第二段、
   迟到的句级文本、以及「先用了 `llm.text` 兜底、随后 tts 句级文本才到」）。现在 `XiaozhiReplyText`
   每上一段就交一次（`XiaozhiReplyOutcome.changed`；没变只记日志），`XiaozhiGateway`
   把首条之后的每一段经 `chatMulti` 的 `onBodyCorrection` 交给流水线，流水线**再发一帧 `TEXT('A')`
   并就地替换 App 的正文气泡**（`resolveTurnBody` 允许同一轮多次上屏，同一段文本只应用一次）。
   因此「兜底先上屏、后面的段再也上不了」不再可能。**同一条机制就是 §6.0 的按段上屏**：首段先交
   （音频侧立即开播），之后每一段各交它**自己**的文本（**不累计** —— 旧版把累积文本一条条发出去，
   在设备屏上就是 A → AB → ABC 的重复气泡，作者已明确否掉）。

结算窗口收敛为三种，**`stop` 是最终结算点**（首段起即可按段交付，见 §6.0）：`stop`（正常，**只补没上屏
的那一段**，各段都已上屏则什么都不发）；`llm` 兜底空闲窗口 8s（整轮没有
任何 `tts` 报文 —— 那种服务端永远不会给 `stop`）；**强制兜底 20s**（收到过 `tts` 报文却一直没等到
`stop`：明显长于正常工具调用/生成，又短于网关 30s 回复超时）。**「最后一句后 2s 即结算」与
10s 的噪声窗口都已删除** —— 它们正是「文本不完整」的成因。

同轮补上「下一轮真机一眼定位」的**全量日志**（不节流、不截断）：每条 `tts` 报文（含完整文本）、
`llm` 报文全字段（`text`/`emotion`）、结算时（触发者 = `stop`/空闲/强制、来源 = tts 拼接/`llm` 兜底/空、
最终正文全文 + 字节数 + 两侧**清洗前后字数**）、以及上屏时 `sendTextFrame` 的**全文 + 字节数 + 分片数**。
清洗器同轮小修（真机模板可能的形状）：全角 `％`、带连字符的工具名、行中紧跟中文/emoji 的裸模板 token、
模板句尾的 `:`，并保持「正常正文的百分号/标点一个都不吃」。

### 6.5 修订（2026-10 真机问题：屏幕文字变动时语音卡顿）—— 正文上屏让路

机制、策略、参数理由、被否决的候选全部写在 **§4.6**（实现位置也在那里）。这一节只记**它与按段上屏/按段播放的关系**：

- §6.0 的**按段上屏不变**：会话层该交多少段还是交多少段（每段只交**它自己**的文本），App 气泡也是
  **立刻**就地替换 —— 被拦的只有**发给设备的 `TEXT('A')` 帧**（也正是唯一会触发设备渲染的那一跳）；
- §4.7 的**句级对齐门已删除**（§4.8 按段播放里段的边界就是权威时刻）；现在只剩 §4.6 的**让路**：
  本段音频还紧（垫底低 / 在途积压 / 距上次上屏太近）时把下一段的字幕攒着（合并成最新一条），
  本段 `tts_stop` 写出时无条件补上；
- 「首段即开播」的延迟收益（~16s → ~3s）一点不受影响；被推后的只是「下一段字幕 + 它的声音」那一小段；
- 「每段字幕一定会出现在屏上」这条硬约束由**本段音频推完时无条件补上**（§4.6）保住，
  而它在按段播放里还是下一段音频的**开播前置条件**（所以不允许长期攒着）。

**真机一眼看的日志**（每次上屏都打两行）：

```
第 N 段字幕上屏(本段 L 字) | 已推送音频≈Xms | 本段起点≈Yms | 音频垫底≈Z 帧(≈Wms) | 在途=I | 距上一音频帧写入 Tms | 队列=Q
小智 TTS 直通:本段字幕已上屏(首次上屏|第 N 段上屏) → 允许开播(当前 BLE 写模式=…)
```

以及首帧那一行多了预充值：`首帧音频写出(距上屏 Xms) 预充=12 帧: …`。
让路时会打一行：`正文上屏让路:暂缓第 N 段字幕(本段音频正紧,不插队) | …`；
补上屏打一行：`正文上屏让路:补上第 N 段字幕(<原因>,本段 L 字)`（原因 = 「本段音频推完收尾」/
「垫底恢复/兜底时限到」）。会话层还另有段级行：`第 N 段字幕上屏(本段 L 字): …` /
`第 N 段字幕更新(本段 L 字)` / `第 N 段字幕(补上:…)` / `第 N 段字幕(跳过:…,不占段号)`。

**按段播放的段日志**（§4.8）另外一行一句地打 `第 N 段开始/收口/推完/播完回报/超时`，
真机上按这几行就能数出「一轮播了几段、每段多少帧、段间等了多久」。

### 7.1 返工修订（2026-10-04，以作者要求为准）

- **小智识别整块 UI 只在「高级」里有一份**：网关设置页不再重复摆「激活状态 / 连接状态 / 说明行」；
  两个 section 共用同一批控件会让同一状态被两处各自拨可见性、行为容易分叉，因此按「只留高级那一份」实现。
- **Device-Id = 已连接对讲设备的真实蓝牙 MAC**（`BleCentral.lastConnectedAddr()`，格式沿用 OTA 的
  `mac` 字段：`XX:XX:XX:XX:XX:XX` 大写）。OTA/绑定与识别 WS 用同一个值；设备未连接时给出可读提示
  并停手，**不**回退手机侧标识（全零匿名 MAC 等）。
- **保存「小智 AI」走设备绑定闸门**（与其它三种网关的「校验-落盘」闸门同一语义）：设备未连接 → 拦截；
  已绑定当前设备 → 直接保存；未绑定/换了设备 → 复用 `XiaozhiActivator` 亮出 6 位绑定码并轮询授权，
  成功才落盘；失败/超时**不落盘**，原配置继续生效并给出可读原因。绑定结果按 MAC 持久化（`xiaozhi_binding`），
  已绑定则不重复绑定。

### 7.2 修订（Device-Id 按当前网关类型决定）

- **Device-Id 按「当前网关类型」决定**，唯一实现是纯逻辑函数
  `stt/XiaozhiIdentity.resolve(网关类型, 已连接设备地址)`（识别 WS、OTA/绑定、设置页显示三处共用）：
  - 网关类型 == `xiaozhi`（「小智 AI」）→ 用已连接设备的真实蓝牙 MAC（归一化后 `XX:XX:XX:XX:XX:XX` 大写，
    与 OTA/绑定同一个值）；取不到 → 失败并给可读原因，**不**回落匿名标识。
  - 网关类型 != `xiaozhi`（OpenClaw / Hermes / 自定义 OpenAI 兼容 / 回显）→ 用全零匿名标识
    `00:00:00:00:00:00`。这些模式仍用小智做**识别**，匿名通道是实测能跑通的形态，因此必须保留。
- 标识在**每次建链时**解析（不在服务启动时固化）：网关类型变化后服务侧丢弃旧热连接并带新标识重连
  （`XiaozhiStt.resetDeviceId()` → `XiaozhiSession.resetDeviceId()`）。
- 绑定/OTA 共用同一套标识：**只有**「小智 AI」做设备绑定；其它网关不绑定、也不需要设备在线。
- 「高级 → 小智识别」的设备 ID 行与实际在用的一致：小智模式显示真 MAC，非小智模式显示
  `00:00:00:00:00:00（匿名）` + 「用小智 AI 作为网关时会改用设备 MAC」。
- 本节取代 §7.1 中「Device-Id 一律用设备真 MAC」的表述。

### 7.3 修订（识别通道必须带「绑定得到的凭据」）

- **OTA 不只是「查激活状态」**：绑定成功后小智云会为该设备下发识别通道凭据（响应里的 `websocket.url` /
  `websocket.token`）。识别 WS 握手必须带它（`Authorization: Bearer <token>`，与官方固件
  `websocket_protocol.cc` 同一规则），否则真 MAC 的整轮识别静默失败（App 只能回「无语音」）。
- 凭据落盘：`stt/XiaozhiCredentialStore`（独立 prefs `xiaozhi_credential`，键 `cred_mac` / `cred_ws_url` /
  `cred_ws_token` / `cred_saved_at_ms`，只存本机、不入库、不进日志 —— 日志只打长度与前 4 位）。凭据带自己的设备 MAC，
  换设备取不到旧凭据（不会拿别的设备的 token 去握手）；`cred_saved_at_ms` 是**落盘时刻**，供 §7.4 的兜底刷新用。
- 建链鉴权唯一决策点：`stt/XiaozhiCredentialGate.linkAuth(网关类型, 凭据, 默认地址, 占位 token)` ——
  小智 AI 用凭据；**没有凭据就不建链**并给可读原因（`MISSING_CREDENTIAL_REASON`，经新增的
  `SttEngine.unavailableReason` 进状态卡文案），**绝不**用占位 token 硬撞云端；
  非小智网关仍走匿名地址 + 占位 token（行为不变）。
- 「云端已激活但本地没有凭据」：保存/激活时**再取一次** OTA 并落盘；仍没有 → 提示
  「云端已激活，但本次 OTA 没有下发识别凭据（websocket.token）：请在 xiaozhi.me 删除该设备后重新绑定一次。」
  （绑定成功但没换回凭据时同样提示）。
- OTA 请求字段单一来源：`stt/XiaozhiOtaRequest`（`name=ai-passport`、`version` = 设备固件版本 → App
  `versionName` → 显式回退、`User-Agent` 同源）；OTA 响应按未激活/已激活两种把键名与结构打进日志用于取证。

### 7.4 修订（识别凭据会过期：自动刷新）

- **token 是按需签发、会过期的**（开源服务端实现为 JWT，`exp` 约 1 小时；官方固件每次 OTA 都覆盖写入
  `websocket` 段）。旧实现把 token 存下来一直用 → 一小时后 WS 因鉴权失败连不上，用户侧又变回「无语音」。
- **两条刷新策略**（纯逻辑 `stt/XiaozhiCredentialRefresh` + 会话层 `XiaozhiSession`）：
  1. **被拒就换**：升级响应 401/403，或对端以鉴权类关闭码（`1008`/`4001`/`4003`/`4401`/`4403`）收掉连接 →
     **重查一次 OTA**（复用 `XiaozhiActivator.queryCloud`，不另写请求）→ 复用 `XiaozhiCredentialStore` 落盘 →
     **用新凭据重连一次**（用户无感，不用手动重绑）。对端的关闭码在 `onClosing` 就处理 —— 实测对端发完关闭帧
     并不立刻结束 TCP，只等 `onClosed` 会错过这个时机。
  2. **保守兜底**：token 的 payload 是**加密**的，App **读不出 `exp`**，所以只能按「存了多久」估 ——
     凭据落盘超过 `XiaozhiCredentialRefresh.STALE_AFTER_MS`（**50 分钟**）时，**下一次建链前**先换一份；
     阈值取 50 分钟 = 短于服务端约 60 分钟的有效期（留 10 分钟余量），又不至于每轮对话都白查一次 OTA。
- **防死循环**：同一次建链尝试**最多刷新一次**（`startTurn` 复位）；刷新后仍被拒 → 放弃并给出可读原因
  （`REFRESH_FAILED_REASON` / `STILL_REJECTED_REASON`，走既有 `unavailableReason` → 状态卡文案），绝不无限重连。
- **匿名通道完全不变**：刷新只对「绑定凭据链路」生效（闸门给出的 `XiaozhiLinkAuth.Ok.refreshable`）——
  非小智网关仍用匿名地址 + 占位 token，**0 次 OTA**（单测钉住）；小智模式**永不**回退占位 token。
- **刷新过程有脱敏日志**：`凭据需要刷新(<原因>) → 重新查询 OTA…` → `已取到新凭据:url=… token=len=N,前4位=xxxx → 用新凭据重连一次`
  （token 只打长度与前 4 位，明文永不进日志）。

## 8. 异常与回退

| 情况 | 行为 |
| --- | --- |
| 未激活 / 激活过期 | 状态卡给出可读原因 + 引导重新激活；对话不可用但不阻断其他网关 |
| WS 断线 | 沿用 `TurnRecovery`（一轮内重连重放一次）；持续失败则提示并可切回其他网关 |
| 凭据过期（WS 被 401/403 拒、或对端以 1008 一类鉴权码关闭） | 重查一次 OTA 换新凭据并用新凭据重连**一次**（见 §7.4）；失败/仍被拒 → 放弃并给可读原因 |
| 小智只回 STT 不回 LLM | 视为失败，提示「小智没有返回回复」，**不发**空气泡 |
| 回的是工具模板/表情（没有可上屏文字） | 两路（tts 句级 / `llm.text`）都取不到可上屏文字时才提示「没有返回可上屏的正文」，原因里写清哪一层为空（§6.3）；**不得**在工具调用静默期提前提示 |
| TTS 无音频或解码失败 | 设备回报 `tts_playback_aborted` → 记录并只保留文字（不回退手机合成，保持行为可预期） |
| 设备不回报 `tts_playback_done`（回不到空闲） | 推空 + 静默 3s 后 App 主动 `tts_stop` 收尾（§4.4「尾部收尾」），设备退出播放态 |
| 打断 | 小智 `abort` + 设备 `tts_abort`，两条路径都要幂等 |

- **JVM 单测**：小智消息解析（stt/llm/tts 状态机）、时序（**按段上屏：每段只交它自己的文本、

  清空缓冲/`tts_stop`）、**噪声句绝不提前交付**（只拿到模板/emoji/空文本时 `changed` 全为 false、
  一次都不上屏也不回退 `llm.text`）、**真机那种 3 段流恰好只上屏 A、B、C 三条**（不存在 AB/ABC，
  段号 1/2/3 与「第 N 段已声明」同号）、**某段缺失时的兜底只补那一段**（不把已上屏的段累计进来），
  、**开播信号只认本轮正文**（`'U'` 识别原文、同为 `'A'` 的提示/兜底文本、本轮正文为空、
  上一轮的迟到信号四类逐项覆盖）、**有可上屏 tts 文本时绝不退化成「没有可上屏正文」**
  （真机字形串：`% get_weather…` + emoji + `<tool_call>` + 句级拼接）、**尾部收尾**（推空+静默判定、
  幂等、迟到帧仍会续一段而不是被切）、缓冲上限与超限丢帧、打断清空缓冲、正文清洗、速率字段映射
  （24 kHz → `rate_khz=24`）、TTS 直通组的帧长/序号回绕；**新增（§4.5）**：写模式契约
  （`TtsWriteModeTest`：小智直通固定带响应写、本机合成仍无响应写且标记待复核）、写分片按 MTU 取值
  （`WriteChunkingTest`：`min(mtu−3, 253)`、协商失败回退 240、MTU 253/256 边界、249B 帧的 1/2 次写临界点

     核对日志（真机要看的几行）：

     ```
     第 N 段字幕上屏(本段 L 字) | 已推送音频≈Xms | 本段起点≈Yms | 音频垫底≈Z 帧(≈Wms) | 在途=I | 距上一音频帧写入 Tms | 队列=Q
     ```

     且**下一段的 `tts_start` 晚于它**（段间是自然停顿）；③ 每段的 `帧数=X` 与设备侧那段收到的帧数对得上
     （不丢帧、不把上一段的尾帧排进下一段）；④ 最后一段结束后出现 `本轮音频收尾`，

     整轮结束时才回 `tts_playback_done`（那就是固件语义与文档不一致，记下 `第 N 段播完回报` 那几行）。

     验收三条：① 设备屏**每一段都出现在屏上**（与 `sendTextFrame … 全文=«…»` 逐字一致；

## 10. 风险与待确认

1. **官方小智云的用量与服务条款**：把 LLM + TTS 也放到云上，是比「只做 STT」大得多的用量；
   一期先按官方默认策略走，若配额/条款有变化再评估自建服务器。
2. **上屏策略**（§6 的**每段独立上屏** + 兜底逻辑）是本设计里最需要你拍板的一处；本轮已按作者口径
   改成「每次上屏 = 那一段自己的文本（A → B → C，不累计）」。
3. **TTS 直通与现有 `DeviceTtsSession` 的耦合**：需要小心保留「`turn_start` 无条件 `tts_abort`」
   这一既有不变量（防止上一轮音频残留）。
4. 小智的 `sentence_start` 文本与 `llm` 文本可能不完全一致（含情绪标记/语气词）：已按 **§6.1** 定案 ——
   以 `tts` 句级文本为准（用户听到的就是它），`llm.text` 只做兜底，`emotion` 永不参与；规则已在 JVM 单测里钉住。
5. **上屏让路的已知取舍（§4.6，作者已接受）**：极端下**某一段的字幕会晚于那一段声音结束**才补上 ——
   用「文字稍晚」换「声音不被文字变动打断」（**文字一定会补上**，且每一段的字幕都是它那段音频的
   开播前置条件，所以不允许长期攒着）。阈值是经验值（垫底 900ms / 在途 4 帧 / 间隔 600ms），
   真机看 `第 N 段字幕上屏(本段 L 字) | … | 音频垫底≈…` 那一行再调：字幕长期上不去 = 阀值过紧，
   上屏时垫底仍常见底 = 过宽。
6. **段起点估值只是证据（§4.7 已作废）**：字幕的时机现在由**段的开播闸门**保证（第 N 段的
   `tts_start` 只在它的字幕已进 BLE 写队列之后才发），不再靠「按播放进度卡时刻」。
   句起点估值（交付那条正文时已收到的帧数）仍进日志（`本段起点≈Yms`）供对照；
   **音频略滞后于文本**时会**低估**该起点（偏早，安全方向），本轮不做补偿。
7. **无法归段的文本的取舍（§4.8/§6.0）**：段界只认小智的 `start`/`sentence_start`（直通侧也是这么
   声明段的），所以 `sentence_end`/`stop` 带来的、与当前段无关的文本**只当本段的新文本上屏**
   （日志 `第 N 段字幕(补上:…)`，段号不变），**不**累计前面已上屏的段；若真机出现「服务端只发
   `sentence_end` 不发 `sentence_start`」的服务端，多句会被并成一段（与直通侧的段划分一致，
   不会串段）—— 真机碰上了再看日志定。
7. **本轮未量化的一点**：固件的 `欠载` 只在每段结束时以**累计计数**回报（`TTS 播放结束: … 欠载=N`），
   **没有逐次时间戳**，所以“开场欠载是否集中在最初 1–2 秒”从现有日志**无法量化**；
   下一轮若要定量，需要固件侧或 App 侧再做一处侧写（本轮范围外）。
